## Rambling

When people talk about low-code, most think of page-building platforms — and many internal tools are exactly that. But visual approaches for logic编排 and BaaS capabilities also fall under low-code. The essence is **"writing less code, using more convenient methods to accomplish what would otherwise require coding."**

Some people love low-code, others hate it. There are those who "pretend" to like it, and those who like it without really understanding why. I'm in the "kind of like it" camp, but only in **"specific domains where delivering requirements faster than skilled engineers writing code is possible."** In these scenarios, it genuinely feels great — and even when it doesn't, the pain is far less than the benefit minus the cost of writing code from scratch. It's well worth making such products enjoyable to use.

Low-code products are actually quite hard to build, especially the big, all-encompassing ones. Too many considerations slow everything down, making them hard to use well. The platform team invests heavily while users urgently need to ship — leading to the paradox where the platform team feels the pain of their investment and users find the tools clunky and blame the dogfood. It often takes a long period of忍耐 before you can "守得云开见月明" (wait for the clouds to part and the moon to shine through). But many projects die before they ever see the moonlight. On the other hand, specialized low-code tools for forms, tables, or charts thrive. Some single-domain BaaS offerings also do well. I personally prefer **"easy-to-use low-code solutions that solve domain-specific problems quickly and lightly."**

There's another misconception: some think low-code is for all engineers. I don't think that's right. Low-code originally aimed to **"let non-programmers build applications quickly without writing code, using views, components, templates, and forms."** We can extend this: low-code suits two types of scenarios — one is **"letting people who aren't domain experts quickly build applications in that domain,"** and the other is **"abstracting protocol models in specific domains to rapidly implement products through low-code."**

I won't go on about the pros and cons of low-code. We already have plenty of internal low-code products that everyone knows well. **Let's look at open-source low-code products and see what we can learn.**

## All-in-One Low-Code Platforms

All-in-one means covering everything from backend to frontend. Honestly, I think this is the hardest type to build, especially in big companies where teams work in silos and multi-team collaboration makes it tough — standards, protocols, and database models are hard to unify. But if frontend and backend are in the same team with a unified model protocol, it's possible. For example:

### [Appsmith](https://github.com/appsmithorg/appsmith)

Appsmith is an open-source low-code framework for building internal applications, created by an Indian startup. It's great for enterprise admin systems — common CRUD, dashboards, data reports, etc. Appsmith feels like an "open-source version" of [Retool](https://retool.com/).

<img src="https://cdn.fliggy.com/upic/gVjjkM.svg" width=800 />

The workflow is similar to conventional development: first, build the UI; second, connect to data sources; third, wire the UI to the data; fourth, deploy — except the coding process becomes a visual one.

<img src="https://cdn.fliggy.com/upic/LRvKll.gif" width=800 />

It also offers plenty of templates for Project, Management Support, Human Resources, Sales, Marketing, Finance, etc. Some of these approaches are worth referencing for low-code projects.

### [Budibase](https://github.com/Budibase/budibase)

Budibase claims to be a low-code platform you'll enjoy using, speeding up application building through simplicity. Compared to Appsmith, it takes a different approach. Budibase has a built-in database, external data sources, a GUI designer, and automation. Its UI creation leans more toward a design-oriented approach, and overall it looks more polished.

<img src="https://cdn.fliggy.com/upic/bDoZda.jpg" width=800 />

### [ToolJet](https://github.com/ToolJet/ToolJet)

ToolJet is another solid low-code framework that supports multiple data sources, uses drag-and-drop for frontend UI (including mobile support), and is JavaScript-friendly.

<img src="https://cdn.fliggy.com/upic/9eo9NR.jpg" width=800 />

Besides these, [nocobase](https://github.com/nocobase/nocobase), [illa-builder](https://github.com/illacloud/illa-builder), and [refine](https://github.com/refinedev/refine) are also worth investigating.

## BaaS Low-Code

I first encountered BaaS (Backend as a Service) around 2019 when working with Serverless. Back then I thought: if only there were great BaaS capabilities, writing FaaS functions would be incredibly smooth.

For quickly building a product, BaaS lets developers focus on frontend development without spending time and effort on backend infrastructure. This enables rapid application development and faster time-to-market. That said, BaaS in China isn't as polished or refined as overseas offerings. Here are some notable foreign ones:

### [Supabase](https://github.com/supabase/supabase)

Supabase is an open-source combination of tools that builds Firebase-like functionality using enterprise-grade open-source products. Firebase is Google's BaaS cloud service that lets developers build apps using Firebase's framework — no servers or infrastructure needed. Understanding Firebase makes it clear what Supabase is.

<img src="https://cdn.fliggy.com/upic/XppYbm.jpg" width=800 />

Its main features include database hosting, authentication and authorization, auto-generated APIs, serverless functions, file storage, etc. Developers don't need to implement these — just call them. It provides client libraries for JS, C#, Flutter, Go, Java, Python, Swift, Rust, and more. See the [docs](https://supabase.com/docs) for details.

<img src="https://cdn.fliggy.com/upic/NiGx5z.jpg" width=800 />

### [Appwrite](https://github.com/appwrite/appwrite)

Besides Supabase, Appwrite is another well-known full backend service — think of it as a competitor. It offers similar functionality, simplifying the tedious process of writing APIs from scratch through a visual interface while maintaining security. It's an end-to-end Docker-based developer platform with containerized microservice libraries for web, mobile, and backend.

<img src="https://cdn.fliggy.com/upic/045fTb.png" width=800 />

It provides account, user, team, database, storage, cloud functions, multi-language support, avatars, and other common services, with corresponding client/server SDKs. Its microservice architecture makes it highly extensible.

<img src="https://cdn.fliggy.com/upic/8Wp6qC.svg" width=800 />

There's also **[SurrealDB](https://github.com/surrealdb/surrealdb)** — an end-to-end cloud-native database for web, mobile, serverless, backend, and traditional applications. It reduces modern application development time by simplifying database and API calls, eliminating the need for most server-side components.

## Headless CMS

Backend developers with nearly 10 years of experience will be familiar with once-popular frameworks like Discuz, DedeCMS, and WordPress. I remember using DedeCMS for commercial projects back in college — fast and smooth. Today, these backend-oriented solutions have evolved further — simpler, more beautiful, and easier to use. Let me briefly introduce Strapi-like headless CMS: content management systems that only provide data, without caring about UI. Content-first.

### [Strapi](https://github.com/strapi/strapi)

Strapi is an open-source headless CMS built with JavaScript. It's flexible, fully customizable, supports many plugins, and can quickly generate REST API services. Overall, it feels familiar to frontend developers — worth a try.

<img src="https://cdn.fliggy.com/upic/IviIfL.gif" width=800 />

### [Cube](https://github.com/cube-js/cube.js)

Cube is a headless business intelligence framework for building data applications. It uses data from any source, organizes it into consistent metrics, and feeds every data application.

<img src="https://cdn.fliggy.com/upic/LhZJs7.png" width=800 />

Beyond Strapi and Cube, you might also try [payload](https://github.com/payloadcms/payload) and [webiny-js](https://github.com/webiny/webiny-js).

## Workflow Orchestration

It seems many companies have their own service orchestration platforms. In larger companies, every BU might have one. But generally, they're hard to make truly usable, and it's difficult to convincingly argue that "service orchestration is faster and more convenient than writing code." Most start off exciting, plateau in the middle, and fizzle out later. It's a long and challenging road, but I look forward to seeing those working on it push through and deepen their capabilities.

That said, in specific workflow domains, some tools do it well — like Automate and n8n. They're worth referencing for workflow orchestration.

### [Automa](https://github.com/AutomaApp/automa)

Automa is a browser extension for browser automation workflows. It uses connected blocks to easily orchestrate common operations — auto-filling forms, taking screenshots, extracting data, scheduled triggers, browser operations, web interactions, etc. It handles repetitive tasks like shortcuts.

<img src="https://cdn.fliggy.com/upic/7lTSua.gif" width=800 />

What it does well is being highly usable while providing plenty of out-of-the-box capabilities, letting people quickly accomplish their needs.

### [n8n](https://github.com/n8n-io/n8n)

n8n is an extensible workflow automation tool. From what I've seen, it handles process-oriented node编排 and logic control quite well, and supports self-deployment.

<img src="https://cdn.fliggy.com/upic/eZ0K1t.png" width=800 />

## Other Quirky Ones

Beyond the common low-code capabilities above, there are three more interesting tools. Notion itself is also a low-code tool (and many people use it that way). Its open-source counterpart is AppFlowy. Then there's YAO, which lets you build various parts of functionality by writing DSL JSON configs. And finally, there's NocoDB — an open-source version of the [Airtable](https://www.airtable.com/) model.

### [AppFlowy](https://github.com/AppFlowy-IO/AppFlowy)

As mentioned, anyone working on low-code should play with Notion — people have done amazing things with it. Also try the open-source AppFlowy to understand how data flows to the UI.

<img src="https://cdn.fliggy.com/upic/LOFHaV.jpg" width=800 />

### [YAO](https://github.com/YaoApp/yao)

YAO is an open-source application engine written in Go. It comes as a command-line tool — download and run. It's suitable for business systems, website/API interfaces, admin panels, and self-built low-code platforms. YAO uses a flow-based programming model where you write YAO DSL (JSON-format logic descriptions) or JavaScript processors to implement various features.

<img src="https://cdn.fliggy.com/upic/SpKs8N.jpg" width=800 />

When I first encountered YAO last year, I was drawn to its innovative approach. Its built-in UI is well-designed, and the installation experience is smooth. For anyone building protocol-driven products, YAO's implementation offers valuable inspiration. For example, the system below was built entirely with JSON configuration — including the UI.

<img src="https://cdn.fliggy.com/upic/n2J5a3.gif" width=800 />

### [NocoDB](https://github.com/nocodb/nocodb)

NocoDB is an open-source alternative to [Airtable](https://www.airtable.com/). What's Airtable? It's a spreadsheet-database hybrid — it has database capabilities but behaves like a spreadsheet. You can combine text, images, links, documents, and various materials in one place. Notion's general approach is similar, but Airtable focuses more on collaborative use cases.

NocoDB turns MySQL, PostgreSQL, SQL Server, SQLite, or MariaDB into smart spreadsheets. The use cases are quite imaginative, as shown in the GIF below.

<img src="https://cdn.fliggy.com/upic/7mUPKT.gif" width=800 />

There's also a rising star in the Airtable-like space called **[ApiTable](https://github.com/apitable/apitable)** , recently open-sourced. It's quite polished overall and highly recommended for experimentation.

<img src="https://cdn.fliggy.com/upic/JmDgxL.gif" width=800 />

## Final Thoughts

Low-code is a highly competitive space. But if you find the right scenario, truly solve real problems, and deliver faster than writing code from scratch, there's plenty of room to thrive. Much of this article is my personal opinion — if you spot anything incorrect, feel free to point it out.
